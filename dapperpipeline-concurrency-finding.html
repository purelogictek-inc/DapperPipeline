PureLogicTek.DapperPipeline 1.9.0 · .NET 10 · finding · 2026-08-23

The shared pipeline

A concurrency test fails intermittently inside DapperPipeline.RunAsync, throwing a different exception each run and passing on retry. Pipeline instances are not shared — they are transient and verified distinct. What two concurrent callers do share is four singleton collaborators, and that is where the two symptoms both point.

Read this first — it corrects two earlier statements of mine

I first said “DapperPipeline is not thread-safe,” then said “production is probably safe because the test shares an instance production wouldn’t.” Both were wrong, and the second was wrong in the reassuring direction. Measurement below: IDapperPipeline is registered Transient, so no instance is shared anywhere — but four of its collaborators are registered Singleton and are therefore shared by every concurrent caller in the process, in production exactly as in the test.

The symptom

One test — two logically identical calls started together and awaited with Task.WhenAll — failed twice with two different exceptions, then passed on a third run with no code change. Different exceptions from one unchanged test is what makes this a race rather than a wrong assertion.

Why run 2 matters more than run 1

ScoringWeight is (string StatKey, decimal Weight) — two columns. The columns Dapper was handed are platform, bench, flex_slot_id, count, position, which belong to a different query in a different command. This is not a mapping error. One operation was handed another operation’s result set.

It threw only because the shapes were incompatible. Two commands whose result sets happened to be type-compatible would not throw — they would return the wrong rows, silently. That possibility is the reason this is filed as urgent rather than as a flaky test.

The pipeline is a stateful builder

Its instance fields, by reflection — this is why re-entrant use of one instance would be unsafe, and why transient registration is the right call:

DapperPipelineContext   _context
PipelineState           _state
List<…>                 _commands            ← ResolveAndRegister appends; RunAsync enumerates
List<…>                 _skippedCommands
Int32                   _scopeIndex
Nullable<Boolean>       _useTransaction
IErrorMapper            _errorMapper

List<T> mutated during its own enumeration produces exactly run 1’s message. But these fields live on an instance that is not shared — so if the state that collided is this state, the sharing must come from somewhere other than DI.

The scanner holds no instance state

Reflection over IParameterScanner’s implementation returned no instance fields at all. A singleton with no instance fields is either genuinely stateless — in which case it is not the culprit — or it memoises in static storage, which reflection over instance fields cannot see. That distinction is the crux and it needs the source.

The hypothesis, stated so it can be refuted

Two concurrent operations meet inside process-wide shared state below the pipeline instance — most likely a non-concurrent memoisation cache keyed by command or row type, held statically or by one of the four singletons.

It fits both symptoms without strain, which is the only reason to prefer it:

  • Run 1 — one thread enumerating a cached collection while another appends to it.
  • Run 2 — a cache keyed by something that is not unique per command, so one operation reads the entry another operation just wrote, and Dapper is handed a deserialiser built for the wrong type. The stack passing through TypeDeserializerCache.GetReader is consistent with the mis-keying happening before Dapper, not inside it.
  • Rarity — a cache is contended only on the first concurrent use of a given key, which is why this needs two operations starting within milliseconds and passes on retry once the cache is warm.
Why this is a production question, not a test question

The four singletons are shared by every caller in the process. Two concurrent HTTP requests have exactly the relationship the two test handlers have. The reason we have not seen it in production is load: one owner, one browser. The test is not creating an unnatural condition — it is the only place we currently run two pipeline operations at the same instant.

What would settle it, in order

  1. Search the package source for static or singleton-held mutable collections — Dictionary, List, HashSet — reachable from RunAsync / ExecCoreAsync, particularly any memoisation of parameter metadata or result-shape by type. If one exists and is not a ConcurrentDictionary, that is the defect.
  2. Check the cache key. Run 2 says an operation received another operation’s result shape. A key that is per-type rather than per-operation, or a shared mutable “current command” slot on a singleton, would do it.
  3. Reproduce deliberately — the same two commands with different result shapes, issued from two threads against one service provider, with the caches cold. If it does not reproduce there, the sharing is coming from our side and we will keep looking here.
  4. Make the failure loud rather than silent. Whatever the cause, the worst outcome is the compatible-shape case that returns wrong rows without throwing. A concurrency guard on the shared structure — or making it genuinely immutable after first build — converts a data-crossing into an exception.

What we will do on our side regardless

  • Keep the failing test. It is the only concurrency coverage this path has and it is earning its place.
  • Not work around it in application code — no locks around pipeline calls — until the cause is known, because a workaround here would hide the production case rather than fix it.
  • Report any further occurrence with the full exception, since the two we have describe the same collision from two angles and a third would sharpen it.
